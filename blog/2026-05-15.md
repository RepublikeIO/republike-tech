## Roles as contracts

### The week in one sentence

The role-and-rights system that powers everything Republike will gate, charge for, or unlock is now structurally complete — modeled on smart-contract semantics, enforced end-to-end in the request path, with rewards and reputation already routing through it.

### A contract-based system of roles and rights

This is the most structurally significant piece of work from this period — and the technical foundation behind Étienne's two announcements.

We built a layered access-control system modeled on the semantics of smart contracts, operating entirely in-database for now — ready for the blockchain tomorrow.

Each Citizen holds one or more contracts that define their role and the associated capabilities. The effective role is resolved at request time from their highest-rank active contract:

- **Free Citizen** — browse, react, bookmark, search, edit profile, post (capped at 3 / day)
- **Citizen** — unlimited posting, moderation voting, governance voting (1× weight), credit earning, reputation accrual, tipping
- **Founding Citizen** — Citizen rights + governance vote ×2 + feed visibility ×2
- **Founding Father** — Citizen rights + governance vote ×4 + feed visibility ×4
- **Founding Consul** — Citizen rights + governance vote ×6 + feed visibility ×8

When a subscription is created, the matching contract is granted automatically (`grantContract`). When it lapses, the role is revoked (`revokeContractsByRole`) — but the contract record stays as an audit trail (status = `REVOKED`, with reason and timestamp; never deleted). Other sources include `TRIAL`, `ADMIN_GRANT`, `PROMOTION`, and one-off `MIGRATION` grants. Contracts expire lazily at read time, so correctness doesn't depend on a cron.

Enforcement: every gated tRPC procedure is wrapped in `capabilityProcedure(<capability>)`, which resolves the role and checks a capability map maintained in code (not in the DB, so the mapping can evolve without migrations). Posting (with per-role rate limit), tipping, moderation and governance voting, rewards claim, reputation accrual — all flow through the same gate.

### Rewards system audit

We audited the full credit-distribution pipeline — from weekly reputation calculation through credit allocation — to verify it composes correctly with the new contract system. Result: credits are now awarded only to users with an active `CITIZEN`+ contract. The weekly reputation pass skips users without a contract at the SQL level; the credit-issuance call gates on `hasMinimumRole('CITIZEN')` before any allocation. No more silent distribution without status verification.

### Privacy: ongoing posture

Privacy hardening continues. This week the pass extended to development environments — test paths that silently bypassed the production-equivalent privacy flow were removed, so the verification flow is now exercised end-to-end, even internally. The same code branch runs in dev, staging, and prod.
