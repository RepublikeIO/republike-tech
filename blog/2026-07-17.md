# Friday, July 17th 2026

## An analytics pipe that can't see you

### The week in one sentence

The analytics pipeline we promised on June 5 and pushed twice finally stood up — and instead of reaching for the off-the-shelf product-analytics SDK that watches every user by name, we built the version that fits the manifesto: a pseudonymous event stream with no user identity in it, whose very first job is measuring where people fall out of onboarding.

### The pipe, finally

The event ingestion path is live. There is a single entry point — a public, unauthenticated `trackProductEvent` mutation — and everything it accepts lands in one place: an `analytics.events` table that lives in its own database schema, deliberately walled off from the application tables.

The shape of an event is small on purpose: an event name, a session id, a timestamp, the platform and app version it came from, an optional funnel step, and a free-form `properties` bag. What is conspicuously absent is anyone's identity. There is no user id column, no email, no handle. The endpoint takes no auth token because it has nothing to attach a token to — the whole point is that the event does not know who you are.

Two design choices are worth naming because they're the difference between "an analytics table" and "an analytics table we can trust":

- **The property bag is sanitised on the way in, not audited after the fact.** The ingestion service carries a hard denylist of keys — `email`, `phone`, `password`, `userId`, `username`, `token`, and their obvious variants — and strips any of them out before the row is written. If a future caller gets careless and passes a PII field in the properties, the field never reaches storage. The safe behaviour is the default; you have to go out of your way to leak, and even then the service won't let you.
- **Every event carries an `insert_id` and the table treats it as unique.** Mobile networks retry; a flaky connection means the same "email submitted" event can be sent twice. The unique constraint plus an `on conflict do nothing` insert makes ingestion idempotent — the client can retry as aggressively as it likes and the funnel counts stay honest. This is the same lesson as the June 5 deploy-pipeline work: the code sitting at a boundary you don't control has to assume the boundary is flaky.

### Onboarding is the first thing it measures

A pipe with nothing flowing through it proves nothing, so we instrumented the surface where measurement actually earns its keep: the signup funnel. When someone drops out of onboarding you want to know *which step* lost them, and until now we were guessing.

The mobile app now emits a clean, ordered funnel as a new user moves through it — intro slides viewed, age submitted, email submitted, email code verified, password set, profile completed, complete. The instrumentation hangs off the navigation layer rather than being sprinkled through every screen: a single hook watches navigation state changes and maps each screen to its funnel step through one small lookup table, so the events stay consistent and there's exactly one place to change when the flow changes.

The session id those events carry is the interesting part. It is **not** a device id and it is **not** a user id. It's a per-session token that rotates daily, so a session can be followed through one sitting of the funnel — enough to see "landed on email, never verified" — but the same person tomorrow is a different, unlinkable session. You can answer "where does the funnel leak" without ever building the ability to answer "what has this specific human been doing over the past month." The measurement we wanted and the surveillance we didn't are two different features, and we only built the first one.

### The views can't see you either

Raw events are one half; the tables the dashboards read are the other, and they got the same treatment.

The pipe exposes exactly two read surfaces to the warehouse, both of them derived views rather than the underlying tables:

- **A daily onboarding funnel**, aggregated to day / event / platform with plain counts — no session ids leave this view at all, so even the loose session-scoped thread is severed at the reporting boundary.
- **A pseudo-anonymised user funnel** for cohort questions ("of the accounts created this week, how many verified their email"). Every row here is keyed by a rotating one-way digest of the user rather than anything identifying — same daily-rotation trick as the client session id, so the same account hashes to a different value each day and the view cannot be used to trail an individual across time. No email, no name, no raw id ever appears in it.

And the account the warehouse connects with is a read-only role that has been explicitly stripped of access to the application schema — it can read the two analytics views and nothing else. The database enforces the privacy boundary; it isn't a convention we're trusting a query author to remember. That's the same posture as the moderation-contract work from June 26 — take the value statement out of the "remember to be careful" column and make it something the system enforces.

### Verification by code, in every environment

Onboarding also grew the piece it needed to actually gate on a real email: a six-digit verification code.

New signups now receive a short numeric code by email — one they type back into the app to prove the inbox is theirs — with the confirmation link kept alongside as a fallback. The email is a plain, localised HTML message (French and English) sent through our existing transactional provider, so there's no new template to manage and the code path is the same in dev, staging, and production.

Two boring-but-real fixes came with it:

- **Codes now actually send outside production.** Our non-production mail has a deliberate gate on it — a safety valve so a stray script on a dev machine can't email real users — but that gate was also swallowing the one message a tester genuinely needs to receive: their own signup code. Signup verification now bypasses that gate specifically (and only for that one purpose), so anyone testing the flow gets their code instead of staring at a screen waiting for mail that was suppressed by design.
- **Email matching got case- and whitespace-proof.** Accounts are stored with a normalised, lowercased email; the verification lookup wasn't normalising the same way, so a code entered from a phone keyboard that helpfully capitalised the first letter could fail to match a perfectly valid account. Trim, lowercase, then look up — the kind of one-line fix whose absence produces a maddening "it says my code is wrong and I *know* it's right" report.
