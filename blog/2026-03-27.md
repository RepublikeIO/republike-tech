# Thursday, March 27th 2026

## Resilience, cost reduction, and laying groundwork for messaging

### Shipped

#### Redis resilience — production hotfix

Production went down on Wednesday. Every page load returned 500 errors. The root cause: our Upstash Redis instance got rate-limited, and the Upstash SDK crashes with `.map is not a function` when it receives a rate-limit error response instead of the expected data format. Since every endpoint in the app touches Redis (feed caching, pinned messages, user profiles, epoch data), the entire app went down.

The fix wraps the Redis client in a JavaScript Proxy that catches all errors on every method call and returns `null` instead of throwing. This means any Redis failure — rate limiting, outage, misconfiguration — results in a cache miss that falls back to a direct database query. The app stays up, just slightly slower. No individual service or endpoint needed modification; the proxy sits at the import level and protects everything.

We also discovered the Upstash instance was created 2+ years ago under a different account. The credentials were manually pasted into Vercel environment variables, and nobody on the current team had dashboard access to the Upstash console.

#### Post topic classification — from LLM chain to embeddings

Every post went through a 5-step AI pipeline in a background job: HuggingFace summarization, OpenAI title generation, HuggingFace language detection, HuggingFace French-to-English translation (because the topic classifier only worked in English), then GPT-4o-mini to pick one of 10 topics. Five external API calls, 3-5 seconds, roughly $0.001-0.003 per post.

We replaced the entire classification chain with a single OpenAI embedding similarity call. On first use, the 10 topic names (with enriched keyword descriptors) are embedded via `text-embedding-3-small` and cached in memory. For each post, we embed the plain text content, compute cosine similarity against the 10 topic embeddings, and pick the best match above a confidence threshold. One API call, under 100ms, roughly $0.0001 per post. The embedding model is multilingual, so the French-to-English translation step is no longer needed.

Title generation (GPT-4o-mini) remains as a separate step but now takes the raw post content directly instead of waiting for a HuggingFace summary.

We wrote 34 regression tests before touching any code — covering the classification contract (text in, topic ID or null out), feed filtering by topic, data shape expectations, and topic data integrity. All tests pass with the new implementation.

The 10 topics are: Culture, Economy, Humor and funny, Irrational and out of the matrix, Other, Politics, Science and technology, Society, Spirituality and Inspiration, Sports. These drive the "Following" feed tab, topic pages, and the onboarding flow where new users pick their interests.

#### Post translation feature re-enabled

The translate button on posts was disabled in July 2025 during a reaction buttons UI redesign. A single `return null` at line 21 with a `// Temporarily hidden` comment, inside an unrelated commit. No linked issue, no explanation.

The backend was fully functional — Google Cloud Translate v2 API integration, database caching per (postId, language) pair, tRPC endpoint. Only the UI was turned off.

We found and fixed 8 issues before re-enabling:

1. The button rendered empty because it used the shadcn `title` prop instead of `children`.
2. "View Translation" and "Hide Translation" were hardcoded in English instead of using i18n.
3. There were two layers of show/hide toggle — one in the parent component, one in the child.
4. When hidden, the translated content was still rendered in the DOM with `display: none`.
5. The language fallback was hardcoded to toggle between English and French. A German user viewing a Spanish post would get an English translation.
6. The Google Translate `translateContent` function had no error handling — API failure crashed the request.
7. The endpoint was a `publicProcedure` — anyone could trigger paid Google Translate API calls without authentication.
8. A hidden `<p>` tag with the translation was rendered when the translation was toggled off.

The fix: single toggle button with i18n strings (added `hideTranslation` and `error` keys in both English and French), always use the authenticated user's language preference as the target, try/catch on the translation API, and `activeProcedure` requiring authentication.

The mobile app already had the translation feature active (never disabled), but it showed the translate option on all posts regardless of language. We added a check so the translate button only appears when the post language differs from the user's app language.

#### Feed and UI fixes

Post deletion wasn't removing the post from the feed visually. The server returned success, the post was deleted from the database, but the React Query cache for the infinite feed query still contained it. The fix iterates all `getBatch` query caches (one per feed tab — best, latest, follows) and filters out the deleted post ID from every page.

Video posts in the feed were aggressively preloading. The MuxPlayer component mounted with no `preload` restriction, immediately downloading adaptive bitrate segments for every video visible in the feed. One page load produced 460 requests and 82MB of transfers. We added viewport gating (only mount the player when the post scrolls into view using the existing `useOnScreen` hook) and `preload="none"` so no video data downloads until the user explicitly hits play.

Removed `console.log` debug statements from the LinkPreview image loading code that were spamming the browser console on every page load in production.

Fixed a React hydration mismatch caused by the CookieConsentBanner. Its Zustand persist store rehydrates from localStorage on the client, producing different HTML than what the server rendered. Wrapped it with `next/dynamic` and `ssr: false`.

#### External service resilience

Beyond the Redis proxy, we wrapped all external service calls in try/catch blocks so no single service failure can crash the app:

- **Inngest** (background jobs): `inngest.send()` failures are logged, post creation succeeds regardless.
- **Algolia** (search): `index.deleteObject()` failures don't block post deletion.
- **Google Translate**: `detectLanguage()` falls back to the user's default language. `translateContent()` returns a user-facing error message.
- **Redis cache service**: Every `getFromCache`, `setInCache`, `deleteFromCache` operation catches errors and returns null/void.

#### Preview environment pattern

Established a repeatable pattern for isolated preview testing on Vercel:

1. Create a Neon database branch from production (instant copy-on-write snapshot, completely isolated).
2. Set branch-specific `DATABASE_URL` and `DATABASE_URL_UNPOOLED` in Vercel for the preview branch.
3. Set production Upstash Redis credentials (cache keys are prefixed with environment name, so no cross-contamination).
4. Push to trigger preview deployment.

This gives a fully functional preview environment with real data, zero risk to production.

### Investigation

#### Real-time messaging feature

We conducted a full technical investigation for adding admin-managed chat channels to the platform. The requirements: admins create channels and invite users, invited users accept or decline, members can send text, images, short video, audio messages, and links. Messages can be edited and deleted.

Current state: the app has zero real-time infrastructure. Notifications are poll-based. The hosting platform (Vercel serverless) does not support persistent WebSocket connections.

We evaluated three approaches:

- **Firebase Data Connect** — Google's new managed PostgreSQL service. Despite the name, it has no real-time capabilities on the Postgres side. Real-time is still only available via Firestore. Also no React Native SDK. Not a fit.
- **Stream Chat** — Turnkey solution with pre-built UI for React and React Native. Fastest to ship but most expensive (~$500+/month at scale).
- **Supabase Realtime** — Connects to any PostgreSQL database, pushes row changes via WebSocket. Same database engine we already use. Free tier covers 200 concurrent connections. SDKs for both React and React Native.

Recommendation: Supabase Realtime. It requires the least architectural change — chat tables live in the existing Prisma schema, CRUD operations go through the existing tRPC API, and only the real-time delivery layer is new. The data model (Channel, ChannelMember, Message, MessageRead) and a 5-phase implementation plan are documented in GitHub issue #24.
