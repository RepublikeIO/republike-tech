# Friday, June 5th 2026

## Leaving Vercel, owning the stack

### The week in one sentence

Republike now runs on infrastructure we operate end-to-end — compute, database, queue, error tracking, and the deploy pipeline that ships them — and the audit that surfaced the move is already pointing at the next pass: anonymous-by-design product analytics.

### The cutover

On Tuesday afternoon, June 2nd, we moved the live site off the managed stack we had been renting (compute, Postgres, queue, key-value cache, error tracking) and onto our own hosts. The window was advertised at ten minutes, came in at twelve, and the only user-visible symptom was a maintenance banner. Posts, sessions, payments, and webhooks all flowed onto the new stack on the first try.

The shape of what we own now:

- A production host that runs the webapp, the background worker that consumes queued jobs, and the scheduler that installs the cron schedule at boot. A reverse proxy in front handles TLS, terminating with an edge-issued origin certificate that is never reachable from the public internet.
- A pre-production host that runs the same trio for `dev` and `staging` side by side. The branches `develop` and `staging` deploy to their respective slot. The branch `release` deploys to production.
- A private cache host that backs both the application cache and the queue. It accepts connections only from the other hosts on its allowlist.
- An observability host running self-hosted error tracking, paired with uptime monitoring and a structured-logs view. Per-project DSNs are environment-tagged so `dev` / `staging` / `production` errors stay separated in one dashboard.

The pipeline that puts code there is now CI-resident. The old flow ran `next build` on the host, which required stopping the live service for a couple of minutes to free RAM for the build — every deploy was a small outage. We moved the build to the CI runner, ship the artifact down as a compressed tarball, and replaced the on-host build with an atomic symlink swap. The HTTP service restart is now in the seconds, not minutes. Rollback is one symlink away, against any retained release.

### What had to be replaced, not just moved

A few pieces of the old stack were tied to the managed runtime model and didn't survive the move intact:

**Background jobs.** The previous queue product webhook'd the webapp from the cloud to fire cron and event-driven jobs; once the webapp moves off that runtime, the events vanish. We ported the recurring jobs that still mattered (epoch creation, weekly reputation, weekly credits, hot-score recompute, top-post digest, monthly rewards sheet, post lifecycle, user deletion, contact-list sync) to queue handlers that share the cache host's connection. A near-equal count of one-shot migrations that had already run on production were deleted from the codebase rather than carried forward as dead conditional branches. Producer call sites became typed enqueue calls; the worker dispatches by name; failed jobs retry with exponential backoff.

**Error tracking.** Cost and sovereignty both argued for self-hosting. The SDK is interface-compatible for the calls we cared about; the migration was a DSN swap per project plus a configuration cleanup. Bumping the SDK to its current major unlocked structured logs, so background-job lifecycle is visible from the dashboard without SSHing into the host.

**Key-value store.** The managed product spoke HTTP. The new one speaks TCP. The change is faster, removes the per-call HTTP overhead, and unifies the cache and queue storage on one box.

**Object storage migration → reverted.** This is the one piece we considered moving and decided not to. Setting up the new bucket and syncing the objects across was straightforward; serving public reads from it was not, because the provider doesn't honour the broad-read ACL we relied on. Bridging the gap required adding a proxy in the webapp and a bulk URL rewrite in the database — a measurable amount of new surface to maintain in exchange for an asset the existing provider already serves correctly for fractions of a euro per month. We rolled the storage migration back and kept what worked. The principle: not every piece of a migration is worth doing. The compute and database moves were the high-value ones.

### Anonymous-by-design analytics

The work we want to spend the coming weeks on is the part of the privacy posture this migration could not fix on its own.

Our product analytics carry a user identifier on every event and ingest into a third-party warehouse. That was acceptable while we were still building the product and the per-user lens was the only way to debug funnels. It's not acceptable as a posture statement — the manifesto says the platform should not track its citizens, and the privacy hardening pass we've been running for the last few cycles ends at this stack if we don't extend it.

The work to come:

- **Identifier strip at the edge.** Events stop carrying any stable user identifier. They carry a session-scoped pseudonymous ID computed client-side and rotated daily; the mapping never reaches our servers. The funnel-level questions ("what fraction of users who saw the paywall completed checkout?") remain answerable; the user-level question ("did this specific person complete checkout?") becomes structurally impossible.
- **Move the warehouse on-stack.** The third-party product goes away. Events ingest into a Postgres analytics schema on our data platform, queried through a self-hosted BI surface we provisioned during the cutover prep. We get the cohort views without sending a copy of every user action to an external SaaS.
- **Enrichment at the source.** The audit also surfaced how thin some event payloads were — failure events carried barely enough to tell a real failure from instrumentation noise. The new event spec moves the diagnostic fields down to the source. None of those fields are PII; together they replace the per-user join we used to need.
- **Differential opt-in for the genuinely user-level signals.** Reputation, credits, contracts — anything that is intrinsically per-user — stays in the operational database and never enters the analytics warehouse. The analytics layer doesn't get to ask user-level questions.

The shape we're after is the same one we used for the contract system: a default that's structurally correct, not a policy that depends on someone remembering to be careful. The platform shouldn't be able to surveil its citizens, not because we promise we won't, but because the data doesn't exist in a queryable shape.
