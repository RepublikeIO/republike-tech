# Friday, June 5th 2026

## Leaving Vercel, owning the stack

### The week in one sentence

Republike now runs on infrastructure we operate end-to-end — compute, database, queue, error tracking, and the deploy pipeline that ships them — and the audit that surfaced the move is already pointing at the next pass: anonymous-by-design product analytics.

### The cutover

On Tuesday afternoon, June 2nd, we moved the live site from Vercel + Neon + Inngest + Upstash to four VPSs we run ourselves on OVH. The window was advertised at ten minutes, came in at twelve, and the only user-visible symptom was a maintenance banner. Posts, sessions, payments, and webhooks all flowed onto the new stack on the first try.

The shape of the new infrastructure:

- **rp-main** — the production webapp, the BullMQ worker that consumes background jobs, and the scheduler that installs the cron schedule at boot. One 8 GB VPS in Gravelines. Caddy in front handles TLS, terminating with a Cloudflare Origin Certificate that's valid for 15 years and stays unreachable from the public internet — Cloudflare in front of us, our cert on the back.
- **rp-dev** — the same trio for `dev` and `staging`, two slots on one host so we keep the cost of pre-prod near zero. The branches `develop` and `staging` deploy to their respective slot. The branch `release` deploys to `rp-main`.
- **rp-redis** — a private Redis used as both the application cache and the BullMQ backing store. It accepts connections only from the four hosts on its iptables allowlist; nothing else can reach it.
- **rp-sentry** — self-hosted GlitchTip for error tracking, paired with the uptime monitor and the structured-logs view that ships with the recent SDK. The DSN per project is environment-tagged so dev / staging / prod errors stay separated in one dashboard.

The pipeline that puts code there is now CI-resident. The old flow ran `next build` on the VPS, which required stopping the live service for a couple of minutes to free RAM for the build — every deploy was a small outage. We moved the build to the GitHub Ubuntu runner (7 GB, no neighbours), shipped the artifact down as a `tar.zst`, and replaced the on-host build with an atomic-symlink swap. The HTTP service restart is now five seconds.

Three workflows — `deploy-dev.yml`, `deploy-staging.yml`, `deploy-prod.yml` — share a reusable `_build.yml` that does lint, type-check, build, asserts `.next/BUILD_ID` exists, and uploads the artifact. The deploy step `scp`s it to `/srv/republike-releases/<env>/<sha>/`, runs `republike-activate`, and prunes back to the last five releases. Rollback is one `ln -snf` from any kept release.

### What had to be replaced, not just moved

A few pieces of the old stack were tied to Vercel's runtime model and didn't survive the move intact:

**Inngest → BullMQ.** Inngest webhooks the webapp from the cloud to fire cron and event-driven jobs; once the webapp moves off Vercel, the events vanish. We ported the 11 functions that still mattered (epoch creation, weekly reputation, weekly credits, hot scores, top posts, monthly rewards sheet, post lifecycle, user deletion, SendGrid sync) to BullMQ jobs that share the rp-redis connection. The other 11 were one-shot migrations that had already run on production — they're now deleted from the codebase rather than carried forward as dead conditional branches. The producer call sites became typed `enqueue(JobName.X, data, { jobId })` calls; the worker dispatches by name; failed jobs retry with exponential backoff.

**Sentry → GlitchTip.** Cost and sovereignty both argued for self-hosting. The DSN swap is a one-line config change per project; the SDK API is identical for `captureException` and `captureMessage`. Bumping the SDK to v8 then v10 unlocked structured logs — `Sentry.logger.info(...)` calls in the BullMQ worker now flow to the GlitchTip Logs view, so background-job lifecycle is visible without SSHing into the host.

**Upstash → ioredis on rp-redis.** Upstash is HTTP. Our prod codebase used the `@upstash/redis` SDK, which is async-friendly but slower per call than a TCP connection. The swap to `ioredis` against rp-redis is faster, removes the per-call HTTP overhead, and unifies the cache and queue storage on one box.

**Vercel Object Storage migration → reverted.** This is the one piece we considered moving and decided not to. We had set up an OVH `rp-storage` bucket and synced 8,171 objects across, then discovered OVH's Standard S3 buckets don't honour the AllUsers ACL — anonymous reads return 403. Serving avatars required adding a webapp proxy, a bulk URL rewrite, and an additional class of cross-cloud failure mode. AWS S3 already worked, costs essentially nothing at our scale, and adds no Vercel dependency. We rolled the storage migration back, kept AWS, and removed the proxy. The OVH bucket stays as a one-week safety mirror, then gets deleted. The lesson: not every piece of a migration is worth doing. The compute and DB moves were the high-value ones.

### Where it gets interesting: the analytics audit

The cutover week ended with a payment-failures incident that turned out not to be a payments incident. The brief read 21 unique users hitting `START_NEW_PLAN_FAILED` over 90 days against 23 successes, called the ratio a P0 regression, and asked for a deploy diff. We pulled the Stripe API directly — the only place ground truth lives — and the picture inverted:

- 18 of 98 non-succeeded PaymentIntents over 90 days were real card declines. Normal card-mix: `generic_decline`, `transaction_not_allowed`, `expired_card`. Not a regression.
- 80 of 98 were PaymentIntents created on component mount that the user never confirmed. Multiple per customer, sometimes 5 in 17 seconds, alternating between plan prices — the signature of someone clicking between plan cards in the paywall.

Half of those came from `LifetimeButton.tsx` in the mobile app, which fired `trpc.payment.createPaymentIntent.useQuery({ price: plan.price * 100 })` at mount and **never used the result** — the actual purchase routes through Apple/Google IAP via `subscribe(plan)`. The Stripe call was vestigial dead code from before IAP was wired in, minting one orphan PaymentIntent per paywall view. The other half came from `LifeTimeCheckout.tsx` on web, which had the same mount-time pattern (less egregious — the PI was at least intended to back the card form). Mixpanel was counting both as `START_NEW_PLAN_FAILED`. There was no payment regression. There was a leaked Stripe object on every paywall render that our analytics treated as user intent.

Two fixes are in flight. The mobile dead hooks are gone — pure deletion, the button still calls IAP, the bundle is smaller. The web checkout now mints the PaymentIntent on click, not on mount, gated by a "Continue to payment" CTA. Both shipped to dev.

### Anonymous-by-design analytics

The deeper issue the audit surfaced is what we want to spend the coming weeks on: our product analytics carry a user ID on every event and lean on Mixpanel SaaS. That was acceptable when we were still building the product and the per-user lens was the only way to debug funnels. It's not acceptable as a posture statement — Republike's manifesto says the platform should not track its citizens, and the privacy hardening pass we've been running for the last few cycles ends at this stack if we don't extend it.

The work to come:

- **Identifier strip at the edge.** Events stop carrying `userId` and `email`. They carry a session-scoped pseudonymous ID that rotates daily and is computed client-side; the mapping never reaches our servers. The funnel-level questions ("what fraction of users who saw the paywall completed checkout?") are still answerable; the user-level question ("did `userId=cmpv…` complete checkout?") becomes structurally impossible.
- **Move the warehouse on-stack.** Mixpanel goes away. Events ingest into a Postgres analytics schema on the OVH Data Platform, queried through Apache Superset (already provisioned during the cutover prep). We get the per-funnel cohort views without sending a copy of every user action to a third-party SaaS.
- **Event enrichment, then strip.** The audit also showed how thin the existing payload was — `START_NEW_PLAN_FAILED` carried only `plan` and library metadata, which is why we couldn't tell a real Stripe decline from a leaked orphan PI without going to Stripe. The new schema adds `decline_code`, `platform`, `app_version`, `checkout_step`, `payment_method_type` at the source. None of these are PII; together they replace the per-user join we used to need.
- **Differential opt-in for the genuinely user-level signals.** Reputation, credits, contracts — anything that's intrinsically per-user — stays in the operational DB and never enters the analytics warehouse. The analytics layer doesn't get to ask user-level questions.

The shape we're after is the same one we used for the contract system: a default that's structurally correct, not a policy that depends on someone remembering to be careful. The platform shouldn't be able to surveil its citizens, not because we promise we won't, but because the data doesn't exist in a queryable shape.
