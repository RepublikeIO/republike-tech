# Friday, June 26th 2026

## Closing the gap between the contract and the code

### The three weeks in one sentence

The thread surface, the translation surface, and the moderation surface all got the same treatment: the brand commitment that the manifesto already made — no popularity sort, no per-user surveillance, no role you didn't earn — was rewritten from a value statement into a piece of code that enforces it without anyone remembering to be careful.

### The thread surface, finally

The comments surface on mobile shipped its long-delayed redesign. The model is one continuous conversation, not a stack of card-boxed sub-posts. A vertical rail runs through avatar centres from the focal post down through every descendant; replies sit on the screen background; the "Replying to @handle" subtitle carries the chain instead of nested indentation.

What that lets us delete is more interesting than what it lets us add:

- **The sort tabs are gone.** They used to read "Hot / Last". "Hot" sorted replies by popularity — the attention-economy mechanic Territory 4 of the brand explicitly rejects. There is no "Quality" tab replacement, either: surfacing a "Respect/Quality" ranking would still be editorialising behind the back of the user, just with kinder words. Replies always surface in the order they were written. The active sort is not selectable because there isn't one to pick — the ordering is transparent and the absence of the control is the statement.
- **The "X commented" indication strip above each post is gone.** The inline reply preview already carries that signal (you see who replied, with their body), so the strip was duplicate signalling that consumed vertical real estate at the top of every card.
- **The "Show 1 replies" CTA is gone.** When the preview already shows all of a post's replies, the toggle is a no-op; we render it only when there are more replies on the server than the inline preview can fit. When we render it, it's pluralised properly — `_one` and `_other` forms via i18next, no "1 replies" string anywhere — and it's the same React component on the feed card, on each reply in the thread page, and on the legacy nested comment view, so the surface stays in lockstep when we change it.
- **Reply reports were missing entirely.** The "..." menu, the report flow, and the delete confirmation are now mounted on every reply, sharing the same `FeedCardMoreOptionsBottomSheet` that posts use — with `isReply` toggled, so the menu surfaces only the actions that apply (Report, Delete-if-mine, Edit-if-mine; no bookmark or copy-link, which only make sense on a top-level post). The server's `reportPost` already accepted any post id — replies are Posts with `parentPostId` — so no server work; the gap was UX.

The accompanying design cleanups land in the same wave: the avatar-to-content gap was halved across post and reply headers, the post-card top padding was rebalanced after we removed the indication strip, the reply composer's "What's on your mind?" placeholder is now properly localised (and properly apostrophised in English; FR was always fine), and the comment surface on the dedicated thread page no longer sits inside a white rounded card with a shadow — that card was misreading the design as a "boxed-off block" rather than a conversation.

### The translation surface, also finally

Translations used to show both the original and the translated text stacked, with the toggle living inside the "More options" sheet. That was three usability mistakes at once: you saw the same content twice; the entry point was buried; and the toggle was tied to a per-post menu rather than the body it controlled.

The new surface is one control, on the body, doing one thing:

- When a post's language differs from the user's UI language, a small globe-line pill appears above the body that reads "Show translation". Tap → fetches the translation → the body **swaps in place** to the translated text, same renderer, same colour, no duplication. Label flips to "Show original".
- The "Translate" option in the more-options sheet is removed. One canonical entry point per action; the menu drops the duplicate.
- Tapping Show translation also auto-expands a truncated post, so the translated body renders end-to-end. A truncated translation is a worse UX than no translation.

The same surface ships with a new anonymous rating endpoint. Below the translated body, "Rate translation 👍 👎". The mutation carries only the postId and the target language — no user identifier — and increments aggregate counters on the `PostTranslation` row. That gives us per-(post, language) quality signal we can use to benchmark translation providers; what it does not give us is "which user thought which translation was bad". The rating column extension to `PostTranslation` (`upCount`, `downCount`) is a small migration that landed on dev, staging, and prod. The Prisma model change is two integers and a default; the design choice it expresses is the same one we made for the contract system and we're heading toward for analytics — useful aggregates, no per-user lens.

### The moderation contract, enforced

The access-control contract has said for some time that `moderation:vote` is a CITIZEN-and-above capability and that `FREE_CITIZEN` does not get it. Two server-side paths were silently violating that:

- **`pickModerators`** — the function that builds the per-post moderator roster — applied a `founderStatus` filter only when `NEXT_PUBLIC_NODE_ENV === 'production'`. In dev and staging the filter was dropped "to make local testing easier", so the roster could pick any active human, including `FREE_CITIZEN` accounts. They got invited, they got the notification, and they crashed into the capability gate when they tried to vote.
- **`firstPostModeration`** — the one-shot onboarding vote — was wired as `protectedProcedure` with an explicit comment saying it was "open to all authenticated users as an onboarding step". The intent was generous; the effect was that the access contract had a hole exactly the size of the onboarding flow.

Both gates now agree with the contract. `pickModerators` runs the same `founderStatus` filter in every environment (the `lastInteractionAt` activity filter stays prod-only so non-prod testing isn't broken). `firstPostModeration` is promoted to the same `capabilityProcedure('moderation:vote')` as the recurring vote; the one-shot service logic (`user.firstModerationVoteAt`) still applies so eligible users only collect the onboarding credit reward once.

The mobile UI got the same treatment a layer up — tapping a moderation notification as a free user now shows a toast instead of navigating into a screen that would 403 the request. The notification surface had stale invitations from before the server fix, and even with those gone, deep links and direct URLs are still possible. Defence in depth, single intent.

### A schema-drift detour that wasn't argon2

In the middle of the moderation work, the dev login broke. The webapp browser flow succeeded; the mobile login, which uses the tRPC `user.login` mutation, returned the catch-all `{success: false}` with no detail. The first hypothesis — argon2's native binary being mis-bundled by webpack — turned out to be wrong; the workspace had already been on the externalised-argon2 config for weeks, and the dev branch's `loginUser` was clean.

The real failure was downstream of the verify call: a `findUniqueOrThrow` on the User table that hit `P2022 — column "User.newOnb" does not exist`. The mock-onboarding experiment had added the column to the Prisma schema, but the migration had never reached the dev or staging databases. Because Prisma's default fetch selects every known column, anything that did a `findUnique{,OrThrow}` on `User` without an explicit `select` tripped on it. NextAuth's `authorize` callback used a hand-rolled `select` and survived; `loginUser` did not.

The fix was migrations, not code: `prisma migrate deploy` against the dev and staging databases, the same against prod once it surfaced there too. The code-level adjustment that does carry forward is the principle: a `findUniqueOrThrow` without `select` is a forward-incompatibility bomb whose fuse is the next schema add — and the mitigation is either `prisma migrate deploy` as part of the deploy pipeline (so the schema cannot land without its migration) or making `select` the default we hold our code to.

This is the part of the week that was nominally "fixing a login bug" and was actually about the deploy pipeline never having a chance to skip a migration.

### A staging build people can hold

Testers had been on a single binary, distinguishable from production only by which API they happened to be pointed at. That made every test session a small ceremony. The fix was a second native target on both platforms — `io.republike.staging` on iOS, `com.republike.app.staging` on Android, both labelled "Republike Staging" — so a tester carries both apps side by side, with distinct icons, distinct push channels, and unambiguous installs. The pipeline produces a signed `.aab` for the Play Console internal track and a signed `.apk` for ad-hoc distribution from the same command (`yarn build:android:staging` and `:apk`), and an `.xcarchive` ready for TestFlight via Xcode Organizer.

The pipeline that got us there is worth a note. The mobile project is on the bare React Native workflow, not EAS; the Republike Expo project is not under our own account, and we deliberately did not go down the route of either getting added to it or migrating it. Targets are configured by the app-side `app.config.js`, `eas.json`, `Podfile`, and the Xcode project itself; bundle ids are platform-keyed so prebuild can't clobber the staging iOS id; a `scripts/dev.sh` switcher lets the developer point Metro at `local | dev | staging | prod` without manual env editing. The result is that "ship a staging build" is one command per platform, not a one-day procedure.

### What's next

- Make `prisma migrate deploy` a pre-deploy step in CI so the dev/staging/prod schemas can never lag the code that selects from them. This eliminates the entire class of P2022 outages we just spent a week on.
- Continue the contract-enforcement sweep into the remaining moderation surfaces: stale push notifications that pre-date the gating fix, the moderation screen self-gating on mount, and the admin moderation tooling that we know currently shows hosts that should not be in the roster.
- ZK identity phase 2 (non-custodial wallets, L2 evaluation) — unchanged, on its own branch.
