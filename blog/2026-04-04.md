## Infrastructure first, features second

### Shipped

#### Admin account recovery endpoint

A user needed to reset their password but had lost access to the email on their account. We had no procedure for this. The password reset flow requires the email on file, and there was no admin endpoint to change a user's email.

We looked at what identity proof we actually store. The strongest signal: if the user has a Stripe subscription, they can confirm payment details that only the account holder would know — last four digits of the card on file, or a recent charge amount.

The new endpoint `POST /api/admin/recover-account` takes a username, a new email, and one or more verification proofs. It checks Stripe card last-4 and recent charge amounts against the Stripe API automatically. It also accepts weaker proofs like the user's referral code or approximate account creation date. One strong proof (Stripe match) is sufficient. Two or more weaker proofs are required if Stripe data isn't available. If verification passes, the email and optionally the password are updated. If it fails, the endpoint returns what checks failed and why.

This highlighted a broader gap: we store almost nothing that can verify a user's identity outside of their email. No phone number, no security questions, no 2FA, no backup codes. The progressive identity layer described below addresses this structurally.

#### Local development stack

We set up a complete local development environment. Docker Compose now runs four infrastructure services: PostgreSQL, Redis, a Serverless Redis HTTP proxy (for Upstash SDK compatibility), and the Inngest dev server. A startup script (`scripts/dev.sh`) brings up all containers, waits for readiness, loads environment variables, runs Prisma migrations, and starts the Next.js dev server.

The Upstash Redis SDK communicates over HTTP, not the Redis binary protocol, so a plain Redis container doesn't work. We use `hiett/serverless-redis-http` as a Docker sidecar that sits between the app and Redis, translating HTTP requests to Redis commands. The app thinks it's talking to Upstash.

We seeded the local database from production — user account, settings, all ten topics, and the current epoch — so the local environment has real data to work with.

For the mobile app, we configured the tRPC client to hit the local backend IP in development mode instead of the production URL. The `ApiProvider.tsx` now uses a `__DEV__` flag to switch between `http://192.168.1.12:9000` (local) and `https://www.republike.io` (production).

#### Design system extracted from Figma

We connected the Figma MCP to Claude Code and extracted the full design system from the Republike Figma file into a reference document in the tech wiki. The Figma file follows atomic design: Brand (typography scale, color palette, logos), Atoms (buttons, inputs, checkboxes, chips, avatars, badges), Molecules (navbar, fields, dropdowns, reaction components, action bars, polls, skeleton loaders), and Organismes (20+ post card variants covering every content type).

Typography values were extracted node by node from Figma: exact font sizes, line heights, letter spacing, and weights for all thirteen type styles from Heading 1 down to Caption Regular. The Figma file uses Graphik Trial and SF Pro, which map to TT Firs Neue in the codebase.

Button specs include exact padding, border radius, background colors, and text styles for all eight type/state combinations across two sizes and two variants. The document maps every Figma token to its Tailwind class equivalent.

### In progress

#### React Native architecture cleanup

The mobile codebase has accumulated partition architecture over the years. Unused dependencies, fragmented patterns, and dead code have built up to the point where adding any new feature (messaging, DID, translation improvements) means fighting the existing structure first.

We started by auditing the dependency tree. The Expo bundler was failing on missing packages (`react-native-worklets`, `copy-anything`) that should have been present — symptoms of a dependency graph that had drifted. Metro cache issues compounded the problem, requiring full cache clears to resolve stale module resolution.

Before we can ship the messaging feature, the mobile translation improvements, or the DID identity layer, the mobile app needs a clean foundation. This means removing unused dependencies, consolidating duplicated patterns, and establishing clear architectural boundaries between features. This work is ongoing.

#### Jira project setup

We created the SCRUM project in Jira and migrated all open GitHub issues from both repositories. Forty issues from `republike-webapp` (21) and `republike-mobile` (19) were created programmatically via the Jira REST API, each tagged with its source repo and linking back to the original GitHub issue. The News feed has no automated ingestion at all.

### Investigation

#### Progressive zero-knowledge identity (did:republike)

We designed a full identity specification for Republike based on decentralized identifiers with progressive zero-knowledge verification. The core idea: users cryptographically own their identity, can prove uniqueness without exposing personal data, and accumulate trust through verifiable actions — with no sensitive information ever leaving their phone.

The system has nine layers, each adding trust and sybil resistance. Layer 0 is a cryptographic root key generated on-device. Layer 1 is email verification (the existing flow). Layer 2 is phone uniqueness via a zero-knowledge proof — the server stores only a salted hash, never the phone number. Layer 3 is device binding through iOS DeviceCheck or Android SafetyNet. Layer 4 is liveness detection with an on-device camera check that produces a ZK proof without any biometric data leaving the device. Layer 5 is document verification — the device scans a government ID with camera and NFC, generates a ZK proof of document validity, and discards the image. Layer 6 is an on-device behavioral AI model that builds a typing and interaction fingerprint over time and periodically generates a ZK attestation of consistency. Layer 7 is peer endorsements from other verified users. Layer 8 is economic staking — locking credits as an identity bond that gets slashed if fraud is proven.

Users progress through layers at their own pace. The system never forces full KYC. Each layer contributes to a trust score that determines platform privileges, from Visitor (read-only) through Citizen, Verified Citizen, and Trusted Citizen, up to Sovereign — the highest tier requiring all nine layers complete.

The specification includes the DID document model, device registry with replay-protected signed updates, mobile-to-web delegated authentication via QR scanning, capability-bounded web sessions, recovery via mnemonic phrase, and a migration path for existing email/password users. Implementation is planned across five phases.
