## Contracts, identity primitives, and the path to a free tier

#### Privacy hardening — ongoing

Continued tightening how user data flows through the system. The principle: personal identifiers should never leave the application boundary in plaintext. This week's pass covered outbound notifications (Discord, Slack), server-side logging, API responses to client apps, and admin export formats. Every channel that previously carried raw identifiers now applies a redaction layer before the data crosses a trust boundary. Also reduced operational noise from third-party payment verification flows — what was a 12-message debug trace per transaction is now a single success or failure signal.

This isn't a one-time fix — it's an ongoing posture. Each time we touch a service that moves user data, we audit the path. The goal is that even if an external channel is compromised (as recent industry events have reminded us is always possible), the data available there is useless without internal context.

#### Elastic paywall — contract-based access control

The largest architectural piece this week. We built a layered access control system modeled on the semantics of smart contracts — roles, vesting, capabilities — without deploying to a chain yet. The design is chain-ready but operates entirely in-database for now.

**The model:**

A `UserContract` is a grant of an `AccessRole` to a user for a period of time. While the contract is active, the user is "vested" in that role and gains its capabilities. When the contract lapses (subscription ends, trial expires, admin revokes), the role is lost — but the contract record stays for audit trail.

Six roles, hierarchical: `FREE_CITIZEN` → `CITIZEN` → `FOUNDING_CITIZEN` → `FOUNDING_FATHER` → `FOUNDING_CONSUL` → `TEAM_MEMBER`. Higher roles inherit all lower capabilities.

Thirteen capabilities gate specific platform actions: `post:create`, `moderation:vote`, `governance:vote`, `rewards:claim`, `credits:earn`, `tips:give`, `reputation:active`, among others. The mapping from roles to capabilities lives in code (not the database) so it can evolve without migrations.

**How it works in practice:**

A single tRPC middleware — `capabilityProcedure('tips:give')` — replaces all the scattered `founderStatus` checks that previously gated features. If the user's resolved role doesn't include the requested capability, the server returns a structured `INSUFFICIENT_ROLE` error carrying the capability name and the minimum role required. The client catches this and shows a contextual upgrade prompt, not a generic paywall.

The session (JWT and profile fetch) now carries the user's resolved access context — effective role, capabilities array, governance vote power, post rate limit. Every component reads this locally via `useAccess().can('capability')`. No per-action API call.

**What's gated:**
- Post creation — rate-limited by role (3/day free, unlimited paid)
- Tips — disabled for free users
- Moderation voting — capability-gated at the procedure level
- Governance — capability-gated with role-weighted vote power
- Credit earning — checked before any credit award
- Reputation tracking — epoch job only processes users with an active CITIZEN+ contract

**Stripe integration:**
- Subscription created (Stripe, Google Play, App Store) → contract granted automatically
- Subscription deleted → all active contracts revoked

**Free tier path:**
- New users can now choose "Continue for free" on the plan screen
- They enter the platform as `FREE_CITIZEN` with limited capabilities
- Every gated feature shows what it takes to unlock it

**Admin:**
- New "Access contracts" tab: summary by status/role, searchable list, per-user detail with full capability breakdown (granted vs. not), grant and revoke with attribution.

Not deployed yet — the full system lives on a feature branch. It requires a migration, a backfill of existing users (911 mapped in dev), and careful validation before going live.

#### Rewards system audit

Investigated the full epoch → reputation → credit distribution pipeline to understand how it interacts with the contract system. Key findings:

- Epochs run weekly (Sundays), triggering reputation calculation across 5 pillars, then credit distribution
- 2,000 credits distributed per epoch to users with non-zero reputation, weighted by `sqrt(reputationScore)` to moderate concentration
- AURE token distribution is deprecated — credits replaced it entirely
- Credits are earned (moderation, referrals, subscriptions, epoch distribution) and spent (tips)
- None of the credit-earning paths previously checked subscription status — anyone active could earn. Now gated by the contract system.

### In progress

#### ZK identity primitives — architectural investigation

We're investigating the migration path toward a zero-knowledge identity protocol. The goal is not "put everything on a blockchain" — it's narrower than that: establish the cryptographic primitives that let a user prove they hold a role (citizen, founder, moderator) without revealing who they are.

The contract architecture we built this week is the first step. The `UserContract` model is shaped exactly like what an on-chain role registry would store — role, grant time, expiry, source, status. When the ZK layer comes in, the write path changes (from Prisma directly to an on-chain transaction confirmed by an indexer) but the read path stays the same. The app never talks to the chain on the hot path.

We're evaluating L2s against the platform's principles: accountable governance (not anonymous consensus), native fee delegation (users never see gas), identity primitives compatible with European regulatory posture, and a sustainable chain that won't disappear in two years.

The custodial wallet model is decided: the server holds derived wallets per user. Users never see seed phrases, never install browser extensions, never know there's a chain underneath. If they want to take ownership of their on-chain identity later, the derived key is theirs — but that's a future feature, not a requirement.

Current work is defining the primitives: what constitutes a "contract" on-chain, what events it emits, what the indexer listens for, and how the role registry maps to verifiable credentials that can be presented in zero-knowledge contexts (moderation votes, governance participation, reputation attestations) without linking back to the user's real identity.
