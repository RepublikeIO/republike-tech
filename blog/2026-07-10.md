# Friday, July 10th 2026

## Two releases and a lap around what we don't own

### The fortnight in one sentence

Two mobile releases went out the door — 1.13 and 1.14, back to back — and each of the three detours that slowed us down was an external dependency changing under us: Google sunsetted Tenor, our old Google Cloud project became structurally unreachable, and an Xcode scheme reference we had never had to look at broke the archive action. The fix in every case was the same shape as the June 5 Vercel move: bring the piece we don't control inside a boundary we do.

### Two ships in one window

Mobile 1.13 landed at the beginning of the window and 1.14 closed it. Neither was a marquee release on its own; taken together they are the version of the app the contract system has been aiming at.

**1.13 — the private-post gate, tombstone counter, and editor stability.**  The webapp side of the access contract had been enforcing "free citizens post PUBLIC only" for a couple of cycles; the mobile composer was still letting a free user pick PRIVATE, then failing at submit with a generic error. 1.13 moves that check up into the composer surface itself: the visibility picker shows the free-tier user only the options the contract will actually let them post, with an inline explanation of what the higher visibilities require. Same enforcement pattern we've been standardising on — the UI cannot offer an action the server would refuse. The tombstone counter that shipped alongside it makes the parent post's "N replies" number consistent with what the reader actually sees — deleting a reply in your own session decrements the counter locally so the row and the header agree, without waiting on a server refetch. The editor stability fixes were the usual TenTap surface: caret-drift after paste, one class of double-tap-eating-a-character bug, and a keyboard-avoidance regression that had crept in during the inline-threads redesign.

**1.14 — inline threads landed, GIF button disabled, composer cleanup.**  The comment-thread work that the June 26 entry described as "the thread surface, finally" was on the release branch but not yet packaged; 1.14 is the version that carries it to the stores. The composer picked up two smaller cleanups in the same release: the "Anonymous" pill was removed from every content-creation surface (four screens, all sharing the same removal) — the primitive existed in the UI but the platform never surfaced anonymous posts, so it was leaking an unfinished capability into the composer chrome; and the GIF button was disabled across all four composers (see below for why).

Both releases followed the pipeline that shipped in the June 26 entry: staging build with `io.republike.staging` / `com.republike.app.staging` alongside the production binaries, signed AAB for the Play Console, and an `.xcarchive` ready for TestFlight. 1.14 is on TestFlight and the internal Play track this week; the store rollouts start next week once the review cycle completes.

The tag graph is now consistent again — `main` at `v1.14.0`, `develop` merged forward to match, and the small archive-action fix (below) already sitting on `develop` so the next release inherits it.

### The webapp caught up on tombstones and GDPR erasure

The webapp had been carrying the older cache-splice-only delete flow — the one where a background refetch against a read-replica could re-surface a post the user had just deleted. Mobile solved this in June with a session-scoped tombstones store that every list surface filters through before rendering. This fortnight the webapp got the same treatment: a Zustand tombstones mirror, a `useTombstoneFilteredPosts` hook, and the same discipline applied to `Conversation` / `ConversationRow` and `PostDetails`. A hooks-order regression showed up on the first pass — `PostDetails` was calling the tombstone hook after an early `return null` when the post id was missing, which threw a rules-of-hooks warning intermittently in dev. The fix is boring (hoist the hook above the guard) and worth mentioning only because it's a good reminder that "we filtered the read" and "we called the hook unconditionally" are two separate correctness properties on the same code path.

Alongside it, GDPR post erasure with Mux cleanup finally moved from ticket to shipped. Deleting a post used to leave the associated Mux video asset orphaned in our video account — invisible to the app, invoicing us monthly, and a genuine problem for erasure requests where the ask was to remove the content from every system it had touched. The erasure path now enqueues a Mux delete job as part of the post-delete transaction, and the ops utilities to find and delete a user by email (three small scripts under `scripts/`) got tidied up and committed alongside — no baked secrets, `DATABASE_URL` at runtime, safe to keep in the tree. The staging tag `v3.0.15` cut earlier this week is the marker for that surface plus the tombstone parity plus the GCP migration below.

### Tenor is being discontinued, and we chose not to swap in a replacement

Around the middle of the window the GIF picker started returning 403 in dev. First hypothesis was a wandering API key restriction; second was a stale IP allowlist. Both turned out to be wrong. Google published a service-discontinuation notice for the Tenor API — the endpoint we were calling is on the sunset list, and no allowlist adjustment brings it back. The API still returns 403 in dev because we don't have access anymore, not because of anything we misconfigured.

The reflex was to swap in GIPHY, and we deliberately did not. Two reasons.

First, the GIF picker was never a high-signal feature on the surfaces where it lived. Composer usage of it was low, and the review of who was picking it and for what suggested it was more of a chrome-completeness thing ("posts should be able to have a GIF") than a genuine authoring lever. Rushing in a replacement to preserve a low-usage surface trades a real integration cost for a marginal-at-best product value.

Second, and more important: the underlying issue is that we treated an external, monetisable, sunsetable API as if it were a piece of our platform. Swapping GIPHY for Tenor keeps that shape — the same dependency, the same key rotation, the same risk of the same sentence one to three years from now. If we want a GIF picker to be part of the platform, the version of that decision that survives is the one where we own the corpus (curate a small in-house set of animated reactions, host them on our object storage, and surface them through a picker we control). That's a real product decision, not an evening's plumbing, so it's on the roadmap rather than on this week's diff.

For this fortnight the concrete change is boring: the GIF button is disabled on both mobile composers and the webapp `RichTextInput`, and the underlying components stay in the tree so we can either re-enable against a self-hosted picker or delete the surface entirely without another archaeology pass.

### Migrating out of a Google Cloud project we couldn't reach anymore

The Google Cloud project we had been using since day one — `brave-embassy-333811`, inherited from an earlier account setup — went from "hard to administer" to "unreachable". The Cloud console returned a Not Found on every navigation, service enablement for Tenor (before we understood the Tenor sunset) returned a load error on the API library page, and the account with owner rights on the project could not reliably authenticate against it. IAM propagation delays that had always been an inconvenience were now a blocker. We were unable to rotate a key or add a service without falling through a hole.

The migration target is `republike-349dc`, a fresh project under the current org and paid account. The move covered:

- **Google Translate** — the projectId used by `google-translate.service.ts` swapped over. Same API contract, new project, same billing separation between `dev` / `staging` / `prod` sheets.
- **Google Sheets** — the ops sheets we write against for rewards and payouts got a new service account (`republike-sheets@republike-349dc`), granted the read-write role on the target sheets, keys deployed to `/srv/republike/{dev,staging,prod}/keys/` on the OVH VPS hosts and consumed via the hardcoded path in the sheets service. The old SA keys are revoked.
- **Google Play IAP verification** — the JWT-signed offline path against `androidpublisher` API was verified end-to-end from prod against the new project. This one was the highest-risk piece — a broken verification path breaks paid subscription onboarding — and it survived the migration on the first attempt.
- **New API keys** — restricted at the Google console to the two VPS egress IPs (`57.128.81.48` for `dev` + `staging`, `57.128.82.168` for `prod`), so a leaked key from a compromised laptop is not a leaked key against the account.

Two detours worth naming honestly.

**A wrong project id.**  The first attempt provisioned against `ambient-scion-492406-p6` — the default project id assigned by the console before it was renamed to `republike-349dc`. The migration commit landed with the wrong id and a `chore(gcp): correct project id to republike-349dc` followed a day later. The mitigation is not vigilance; it's what we should have done in the first place: read the project-selector after the rename, not the URL bar during it.

**A five-attempt SA key create.**  The service-account creation call succeeded and returned a real id; the subsequent `keys create` against that id returned `NOT_FOUND`. IAM propagation delay — a known Google-side quirk — but not one the provisioning script handled. We patched the script with a retry loop (five attempts, ten-second sleep between them) so the first-run experience of the next fresh project is "wait a minute" rather than "the console lied and now the script bails halfway through provisioning". Same pattern as the deploy-pipeline lessons from June 5: the code that runs at a boundary we don't control needs to expect the boundary to be flaky.

The `.gitignore` also picked up an `scripts/*-key.json` guard so a well-intentioned `git add -A` cannot roll a live SA JSON into a commit.

### The iOS scheme detour

One local detour that isn't external and is worth writing down anyway. The first iOS production archive attempt failed with exit 66 and the not-obviously-related error message: `Scheme republike is not currently configured for the archive action`. Xcode surfaces this the same way whether the scheme is missing the Archive step or whether the scheme references a project that doesn't exist; the second case is much rarer, so the reflex is to open the scheme editor and inspect the actions.

The actual failure was that the scheme file at `ios/republike st.xcodeproj/xcshareddata/xcschemes/republike.xcscheme` held four `ReferencedContainer = "container:republike.xcodeproj"` attributes — pointing at a directory that does not exist on disk. The real project directory is `republike st.xcodeproj`, with the space, and the workspace `.xcworkspacedata` already had it right (`group:republike st.xcodeproj`). At some point the scheme was regenerated or hand-edited against the old path and the discrepancy was invisible to every action except `archive`, which is the one that walks the container graph strictly.

Fix: rewrite the four references to point at the correct path, kill the scheme's `.bak` sibling, commit on `develop` so the next release inherits it. Total time to root-cause once the reflex to inspect the scheme editor was overridden: five minutes. Total time in the reflex first: too long. The lesson-shaped thing is the same as the P2022 login bug from June 26: an error message that describes a symptom accurately but obscures the mechanism steers debugging toward the wrong shape. The mitigation isn't a better error message; it's committing the scheme file to source control (it now is) so this failure mode cannot silently reappear when a machine regenerates the scheme locally.
