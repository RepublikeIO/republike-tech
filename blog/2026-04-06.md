# Sunday, April 6th 2026

## Subscriptions, mobile, and a long week of cleanup

### Shipped

#### Post deletion fix — server-side cache was the root cause

Deleted posts were persisting in the feed across all tabs despite being marked as removed in the database. The client-side React Query cache invalidation we initially added wasn't the fix — the real problem was server-side. The `deletePost` service marked posts as `isRemoved: true` but never invalidated the Redis feed cache. Every feed request kept serving the cached version with deleted posts still in it.

The fix adds `cacheInvalidation.handleCacheInvalidation('post:delete', ...)` after the soft delete. All feed caches are flushed, so the next request from any client — web or mobile — fetches fresh data from the database.

On the mobile side, we also added optimistic removal: the deleted post is filtered out of all cached infinite query pages immediately, so the user sees it disappear without waiting for a network round-trip. Built a shared `feedCacheUtils.ts` with `removePostFromFeedCache`, `updatePostInFeedCache`, and `incrementReplyCount` — reused across delete, reactions, and reply flows.

#### tRPC version mismatch — mobile mutations broken since v11 upgrade

The webapp was upgraded to tRPC v11 but the mobile app stayed on v10. tRPC v11 changed the HTTP protocol for mutations — v10 clients send mutations as GET requests that v11 servers reject with "Unsupported GET-request to mutation procedure." This meant post deletion (and potentially other mutations) was silently failing on mobile in production.

The fix enables `allowMethodOverride: true` on the tRPC handler, making the v11 server accept both v10 and v11 client request formats. A proper fix would upgrade the mobile app to tRPC v11, but that's a larger migration.

#### Feed performance — eliminated N+1 queries and infinite refetch loops

Every post in the mobile feed triggered its own `getUserProfile` API call to fetch badge types and mute status — data that was already included in the feed response. With 20 posts visible, that's 20 extra round-trips on every feed load. The badge data was already available via `user.badges` in the post data. The mute check was redundant because the backend already excludes muted users from feed results. Removed the per-item query entirely.

The loading skeleton was replacing the entire feed on pull-to-refresh (`isRefetching` triggered the skeleton). Now it only shows on initial load when there's no data yet.

#### Killed query flooding across the app

Multiple screens had `staleTime: 0` and `cacheTime: 0` on their queries, which means React Query considers data stale immediately on every render, triggers a refetch, the refetch causes a re-render, which triggers another refetch — an infinite loop. This was flooding the database with identical queries nonstop.

Affected screens and the fix:
- **Feed tabs** (`HomeFeedScreen`): `staleTime: 0, cacheTime: 0` on `getBatch` infinite query. Removed — queries now use `refetchOnMount: false, refetchOnWindowFocus: false`, only refresh on pull-to-refresh.
- **Profile screen** (`useProfile`): `staleTime: 0` on both `getMyUserProfile` and `getUserProfile`. Plus `getUserFollowers` and `getUserFollowings` firing with empty `userId` before the profile loaded. Fixed with `enabled: !!userId` guards and removed aggressive refetch settings.
- **Profile activity tabs** (`ProfileActivity`): three tabs (Published, Commented, Rewarded) all had `staleTime: 0, cacheTime: 0` on `getUserPosts` infinite queries. Removed — data loads once per tab.
- **useMyProfile hook**: had a `useEffect` that depended on `queryInfo` (which changes every render) calling `refetch()` — a direct infinite loop. Removed the effect entirely.
- **Search posts** (`SearchPost`): `isLoading || isRefetching` showed skeleton, which unmounted the FlatList, which remounted and triggered refetch — loop. Fixed with `isLoading && !posts` guard and `enabled: query.length > 0`.

The root principle: queries should fetch once and stay until the user explicitly asks for fresh data. No timers, no stale checks, no automatic refetching on re-render.

#### Atomic feed cache updates for reactions and replies

When a user reacts to a post or comments on the detail page, then navigates back to the feed, the counters now update without a full feed refetch. After a successful reaction, the specific post's counter is incremented directly in every cached feed page. After a successful reply, `nbReplies` is incremented the same way. All through the shared `feedCacheUtils.ts` utility.

#### Android keyboard — editor toolbar stays visible

The content creation toolbar (camera, gallery, GIF, poll icons) was disappearing behind the keyboard on Android. The toolbar was wrapped in its own `KeyboardAvoidingView` which conflicted with `adjustResize`.

The fix: `adjustResize` in AndroidManifest (unchanged from original) + `KeyboardAvoidingView` at the screen level with `behavior={Platform.OS === 'ios' ? 'padding' : undefined}`. On Android, `adjustResize` handles the resize; on iOS, `KeyboardAvoidingView` with `padding` does. The toolbar is inside the resizing container, so it moves up with the keyboard.

Applied to: `ContentCreationScreenWithTenTap`, `ContentCreationScreenPollSurveyTenTap`, `ContentCreationScreenV4`, `RepostContentCreationScreenWithTenTap`, `PostFeedDetailScreen` (reply input).

`LoginScreen` and `ForgotPasswordScreen` had `KeyboardAwareScrollView` commented out — restored with `enableOnAndroid`. All TenTap editor instances had `avoidIosKeyboard` disabled — enabled.

#### Feed card spacing tightened

The vertical spacing between post content and the action bar was too large, especially when posts contained hashtags. Three sources of wasted space:
- The HTML renderer (`mergeParagraphsWithBr`) was converting `</p>` to `<br><br>`, adding a blank line after every paragraph including the last one. Changed to single `<br>` and strip all trailing `<br>` from the end.
- The feed card had `py-5` (20px top and bottom padding) and `gap-y-2.5` between content and footer. Changed to `pt-4 pb-2` and `gap-y-1`.
- The detail page had `pb-5` on the text container and `gap-3` on the card. Changed to `pb-1` and `gap-1`.
- Link preview had `marginVertical: 10`. Changed to `marginTop: 4, marginBottom: 0`.
- The `@username` text was the same size as the display name. Changed to `text-xs font-SFProRegular` with `-mt-1` to tighten the gap.

#### YouTube Shorts support

YouTube Shorts URLs (`youtube.com/shorts/VIDEO_ID`) weren't being detected — the video ID extraction regex in `usePreviewLinks` only handled standard YouTube URL formats. Added `/shorts/` to the split pattern. Shorts now render the embedded YouTube player like regular videos.

#### Search empty states

The search tabs (Posts, Accounts, Tags) showed blank screens when there were no results or no query. Added empty state views: "Search for posts, people or hashtags" before typing, "No results found" after a query with no matches. Also added `enabled: query.length > 0` to prevent firing search queries with empty strings. Added i18n keys in both English and French.

#### Back button tap area

The back button in the navigation header was hard to press — the touch target was only the 24px icon. Added `hitSlop={16}` for a 16px invisible touch zone without changing the visual size of the nav bar.

## Subscription lifecycle — the bug we couldn't see, and what we changed

The biggest piece of work this week wasn't a feature — it was an investigation into our subscription state machine that started from a single piece of feedback ("my subscription says it's expired but I just paid") and ended with several days of code changes spanning the webapp, mobile app, and Stripe webhook handler. We're writing this section more openly than usual because the lessons matter more than the bugs.

### What was happening

The user-visible symptom was simple: a small number of subscribers were ending up in a state where their app showed them as expired or trial-ended, even when they had a valid charge in Stripe. Some hit the paywall after a successful renewal. A few founding members lost their badge. For everyone affected, the fix was the same — restore the right state by hand — but the underlying causes were spread across half a dozen places, and we hadn't built the tooling to detect drift between Stripe and our own database.

We did not (and still don't) want to share names, customer IDs, counts, or amounts. Those belong to the people they belong to, and publishing them would compound the harm. What we can share are the failure modes themselves and the fixes, because those are the parts that other teams running Stripe in production will recognize.

### Root causes, in plain terms

There were four distinct bugs interacting with each other. None of them was catastrophic on its own. Together they produced a state machine that could drift away from Stripe and stay drifted.

**1. The webhook handler had a fall-through.** Our `handleStripeEvents` function was a long switch statement covering every Stripe event we cared about. Several of the case branches were missing `break` statements, so one event would silently execute the handler for the next event below it. In practice this meant a `customer.subscription.updated` could run alongside a `customer.subscription.deleted` handler on the same payload. Sometimes the second handler nulled out a field the first one had just set. Adding the missing `break`s closed half of the drift.

**2. The synchronous payment flow assumed an async webhook had already arrived.** When a user completed checkout in the webapp, we wrote to the database based on the assumption that Stripe's `customer.subscription.created` webhook had already been processed by the time the redirect resolved. In practice the webhook sometimes arrived a few seconds later. The redirect would then read stale data, decide the subscription wasn't active yet, and route the user to the paywall — even though their card had just been charged. We rewrote the flow to write the row synchronously inside `handleSubscription` from the data we already had in hand, so the local state is correct the moment Stripe confirms the payment intent. The webhook still runs and reconciles.

**3. A Stripe API combination that the dashboard quietly forbids.** Our payment intent creation was setting both `payment_method_types: ['card']` and `statement_descriptor: 'Founding Father'`. The Stripe API rejects this combination — you can't set a custom statement descriptor on a card-only intent, you have to use `statement_descriptor_suffix` instead. This was failing for a specific founder-tier purchase path, returning a tRPC error to the client and leaving the user with no useful next step. Switching to `statement_descriptor_suffix: 'Founding'` resolved it.

**4. The redirect happened before the session updated.** On the client side, the Stripe checkout form was redirecting the user to the success page before our NextAuth session had been refreshed. The success page would then read the old session, see no active subscription, and bounce the user back. Reordering the calls — `await updateSession()` first, then `router.push()` — fixed it.

### Detecting the affected users without making it worse

Once we understood the failure modes, we needed to know who was affected. The instinct is to write a script that mutates state to "fix" everyone in one pass. We resisted that because it's exactly the kind of script that, run with one wrong assumption, makes a small problem into a big one.

Instead we wrote a read-only audit. The script reads from the database and from Stripe, joins them on customer ID, and produces a CSV of users whose local state doesn't match Stripe's view of their subscription. It does not write anything. It does not surface user identities in the output beyond what's needed to act on a single row. We reviewed the output by hand and triaged each case individually, restoring state on a per-user basis after confirming the desync was real and the user was actually owed the higher state. A few cases turned out to be legitimately expired and stayed that way.

We did not publish the audit. We did not pipe it to a dashboard. The output went to a single private location and was deleted after the remediation was complete.

### What we changed structurally

Beyond the four root-cause fixes, we added two structural changes that should make this class of bug visible if it ever returns:

**A new "subscription ended" landing screen on mobile.** Previously, a user whose subscription had been canceled or expired would get bounced to the paywall with no explanation, which is confusing and feels punitive. The new `SubscriptionEndedScreen` is an empathetic dead-end with a clear "renew your membership" CTA that pre-selects the user's previous tier and skips the trial step (you don't get to start a free trial twice). The renewal flow has its own polling logic to handle the case where Stripe takes a few seconds to confirm the charge, with a fallback UI if the poll times out instead of leaving the user staring at a spinner forever.

**An Inactive-user trap at the API layer.** We added a global tRPC error link in the mobile API provider that watches for `USER_INACTIVE` errors on any request. When one comes in, the user is force-routed to `SubscriptionEndedScreen` instead of seeing a generic "something went wrong" toast. The same hook handles 401s by triggering a clean logout. The point is that no matter where in the app the user is when their state goes stale, they end up somewhere they can recover from, not somewhere they have to figure out themselves.

### What we owe the people who were affected

A few things we want to be plain about, because we'd want other teams to be plain in our shoes:

- **It was our bug, not theirs.** No user did anything wrong. The fact that some subscribers had to email us to be told their state was wrong is on us, not on them.
- **Restoration was retroactive and complete.** Where someone lost a tier, paid status, or founder badge they were entitled to, it was restored — including badge state where applicable. Where someone was double-charged, the duplicate was refunded directly through Stripe.
- **We changed the system, not just the data.** Patching the database without fixing the code that wrote the bad data would have guaranteed a repeat. The four root causes above are all in production now. The audit script is committed, parameterized, and runnable on demand against any environment.

### What we'd do differently

The honest answer is that we should have built the audit tooling before we needed it, not in response to a specific complaint. Reconciliation between a payment processor and a local database is the kind of thing that's invisible until it isn't, and the right time to write the read-only diff script is the same week you wire up the first webhook, not the week your first user notices something is wrong. We've added "build the reconciliation diff" as the first step in any future work that touches the subscription state machine. It's one of the few engineering rules we now consider non-negotiable.

We're also rebuilding our staging environment so it can be flipped through every subscription state in seconds — expired, active, trial, founding, canceled, mid-renewal. The ability to drop a test user into any of these states without manual SQL means the next time we change the webhook handler, we can verify the matrix instead of hoping. That work lives in `scripts/seed-staging-test-user.mjs` and `scripts/set-staging-user-expired.mjs` and got a heavy workout this week.
