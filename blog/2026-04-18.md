## Mobile release, subscription governance, and the reputation system enters the admin

### Shipped

#### Mobile v1.2.1 — Expo SDK 53 upgrade and Play Store compliance

The mobile app jumped from Expo SDK 52 to SDK 53. That means React Native 0.76 → 0.79, React 18 → 19, Kotlin 1.9 → 2.0, and a full iOS native regeneration from the SDK 53 bare template. This wasn't optional — Google Play began enforcing 16 KB memory page size alignment for all submissions targeting Android 15, and the prebuilt native libraries in RN 0.76 were 4 KB aligned. Every `.so` in the AAB was failing the check.

The upgrade path was incremental: SDK 52 → 53 (not 55), because 53 keeps Reanimated on v3 (not the v4 breaking change) and uses RN 0.79 which has 16 KB support without requiring the New Architecture. Even so, the migration surfaced a chain of compat issues:

- **`react-native-network-logger`** reached into an internal RN path (`Libraries/Network/XHRInterceptor`) that moved in 0.79. The library is unmaintained. Removed it entirely along with the debug screen and floating button that used it.
- **`babel-plugin-react-compiler`** was emitting code that accessed `React.__SECRET_INTERNALS_DO_NOT_USE_OR_YOU_WILL_BE_FIRED.ReactCurrentDispatcher` — a React 18 internal that was restructured in React 19. The vendored `react-compiler-runtime` shim was explicitly a React 18 polyfill. Removed both; React 19 ships the compiler runtime natively.
- **`@10play/tentap-editor`** had `react-dom@18` as a hard dependency (not peer), so yarn installed a nested copy. React 19 at the top level + React 18 inside tentap = two React runtimes fighting over internals. Fixed with a `resolutions` block forcing `react` and `react-dom` to 19.0.0 everywhere.
- **`react-native-iap`** 14.4+ switched to Nitro Modules which require the New Architecture. Since we're on legacy arch, we pinned to 13.0.4 — the last pre-Nitro version that compiles cleanly against Kotlin 2.0.
- **`react-native-modal`** 13.x called `BackHandler.removeEventListener`, which RN removed in 0.74. Bumped to 14.0.0-rc.1.
- **Kotlin 1.9.25 → 2.0.21** — required for `expo-updates`' KSP plugin to work on SDK 53.

On iOS, `expo prebuild --clean` regenerated the native project with the new Swift `AppDelegate` (SDK 53 changed the window lifecycle so `ExpoAppDelegateSubscribers` fire after the window exists, not before). The old ObjC `AppDelegate.mm` was causing a `fatalError("Cannot find the keyWindow")` crash at boot because the dev launcher subscriber ran before the window was created.

CocoaPods 1.16 introduced stricter subspec xcconfig merging that broke `expo-dev-menu`'s `DEFINES_MODULE` declarations across its Main/SafeAreaView/Vendored/ReactNativeCompatibles subspecs. The fix was a patch (via patch-package) that removes the per-subspec `DEFINES_MODULE` overrides, letting the root spec's declaration propagate cleanly.

Other fixes that landed with the release:

- **FOREGROUND_SERVICE_MEDIA_PLAYBACK stripped.** Play Console was gating every submission for a video demo of background playback. The permission existed because `expo-video`'s config plugin had `supportsBackgroundPlayback: true`, but nothing in the app actually uses background playback. Flipped to `false` and added a `tools:node="remove"` in the manifest.
- **Edge-to-edge bottom tab bar.** SDK 53 enables edge-to-edge on Android by default. The tab bar's fixed 64px height was being occluded by the system nav bar. Added `useSafeAreaInsets()` to pad the bottom dynamically.
- **Edit Profile save button.** The form validation schema required `username` (non-empty + regex), but the field is `editable={false}` and some accounts have no username. The button was permanently disabled. Made `username` optional in the schema and stripped it from the mutation payload entirely — the field is read-only, it shouldn't gate submit.
- **Keyboard handling on Edit Profile.** `react-native-keyboard-aware-scroll-view`'s Android mode was effectively a no-op without `enableOnAndroid`. Added it plus `extraScrollHeight`.
- **Button component default padding.** The `cva` base variant had `py-3` but no `px-*`, so buttons collapsed to text-only width. Added `px-4`. Disabled flat buttons now dim via opacity instead of getting a grey fill.
- **FeedListItem missing key.** The `key` was on the inner `FeedCardTextContent` instead of the outer `Pressable` returned from `.map()`. React never saw it.
- **ProfileActivity hooks-after-early-return.** A `useCallback` was declared after an `if (isLoading) return <Skeleton />`, so the hook count changed between renders. Moved all hooks above the early return.
- **HamburgerMenuScreen blank on iOS.** Was importing `SafeAreaView` from `react-native` (deprecated, collapses to zero height on RN 0.79 + react-native-screens 4.x). Switched to `react-native-safe-area-context` with `edges={['left', 'right', 'bottom']}` to avoid double-counting the nav header inset.
- **NSContactsUsageDescription missing.** `expo prebuild --clean` wiped the old Info.plist. The `expo-contacts` plugin wasn't declared in `app.config.js`, so the regenerated plist had no contacts permission string. Apple rejected. Added the plugin + the key.

The AAB ships as versionCode 23, versionName 1.2.1, signed with the correct upload key, all 18 `.so` files at `0x4000` alignment. Firebase was already removed in the previous cycle so the advertising ID declaration is clean.

#### Subscription audit — CEO decision workflow

The audit tab in the admin app now lets the CEO pick a resolution path for each drift case without triggering the remediation immediately. The goal is separation of judgment from execution: review all cases at your own pace, record your decisions, then batch-apply when ready.

**How it works:**

Each audit row now shows a dropdown of candidate resolution paths (computed server-side per drift type — e.g. a DUPLICATE_SUBSCRIPTION row offers "Cancel duplicates" or "Manual review", not the full action list). The CEO picks one and clicks Save. The decision is persisted in a new `SubscriptionAuditDecision` Prisma model keyed on `(userId, driftType)` with `decidedByEmail` for attribution. The choice is recorded but **not applied** — `appliedAt` stays null until a future batch-apply step walks unapplied decisions and dispatches the existing remediation handlers.

The decision-save endpoint validates the chosen action against the candidate list server-side (can't smuggle an unsupported action), and refuses to overwrite decisions that have already been applied (irreversible).

**Caching fix:** the audit's Redis cache now stores only the raw drift data (the expensive Stripe scan). Decisions are hydrated fresh from the DB on every read. Saving a decision no longer busts the 30-minute audit cache — only an explicit refresh or TTL expiry triggers a re-scan.

**Stripe rate limiter:** the audit was hammering Stripe past its 25/sec test-mode limit. Added an env-aware rate limiter that detects `sk_test_` vs `sk_live_` from the key prefix and caps at 80% of the allowed rate (20/sec test, 80/sec live). All three Stripe call sites (`subscriptions.list`, `invoices.list`, `customers.list`) route through a promise-chain gate with automatic single-retry on 429 errors.

**Env-mismatch handling:** running the audit locally with a test-mode key against a production DB (live customer IDs) was flooding logs with per-user "No such customer" errors. Now we tally those silently and log one summary line at the end.

**Label clarity:** "Orphan subscription" → "Disconnected accounts". "Link Stripe" → "Reconnect payment". The descriptions are honest about the webhook bug being the root cause, not hand-wavey about the connection being "lost or never established."

**Diagnosis column:** a new column between Remediation and Resolution shows the drift label, a plain-language explanation of the problem (including why it happened), and what each fix option does. Gives the CEO full context to make an informed choice without needing to consult a developer.

#### Reputation system — admin management panel

The reputation system was ~75% functional but completely invisible to the admin. Three of five pillars compute real scores (Quality, Wellbeing, Altruism), two are stubs (Respect, Competence). The weekly Inngest job runs, scores are stored, the leaderboard works. But there was no way for a non-developer to understand the algorithms, see their health, or experiment with changes.

**What we built:**

A new "Reputation" tab in the admin with three layers:

1. **Pillar health overview.** Five cards showing average score, min/max range, and user count per pillar. The two unimplemented pillars are visually distinct (dashed border, "Not yet implemented" label). A score distribution histogram shows how the global scores are spread across 10-point buckets. Coverage percentage tells you what fraction of active users even have a reputation score.

2. **Leaderboard.** Paginated, searchable table of users ranked by global reputation score. Each row shows the per-pillar breakdown from the latest epoch, founder status, and membership date. Click a row → user detail panel with full epoch-by-epoch history and trend arrows (↑/↓ vs previous epoch).

3. **Algorithm detail pages.** Click any pillar card on the overview → navigates to a dedicated page for that algorithm. No compressed text descriptions — the tech spec is rendered as structured UI:
   - **Data source** — which tables are queried, what fields are read, what the time scope is (epoch-bounded or all-time), with relevant notes (e.g. Quality is all-time accumulative, a single bad-faith campaign has permanent drag)
   - **Computation** — numbered step list showing exactly what happens to the raw data. For Quality: a 3-column reaction weight table (positive/neutral/negative, color-coded, sorted by severity). For Wellbeing: a 5-row table showing each activity type, which Prisma table it queries, and the filter condition. For all threshold-based pillars: the mapping table from count → score.
   - **Formula** — rendered as a styled monospace block: `score = tanh( Σ(weight × count) / 30 ) × 100`
   - **Output range** — bounds, precision, whether discrete or continuous, and operational implications

4. **Simulation sandbox.** Each pillar detail page has editable parameters (reaction weights, tanh factor, threshold values) and a "Run simulation" button. The simulation endpoint fetches raw user data for a sample (cached 10 min in Redis), re-scores with the overridden params, and returns a before/after comparison: average score delta, biggest gainer, biggest loser, and a per-user table sorted by impact. The point is to let someone experiment with "what if DECEPTIVE was -10 instead of -5" and see how many users are affected before committing to a change.

**Privacy:** All user emails in the admin are now masked (`adr***@rep***.io`). Usernames take display priority over real names wherever a user is identified.

### What's next

- **Respect and Competence pillars.** The algorithms need definition. The admin panel makes the gap visible — those two cards sit there with dashed borders saying "not yet implemented," which is the point. The simulation sandbox is ready for when the formulas are decided.
- **Batch-apply for audit decisions.** The decisions are being saved but there's no "apply all unapplied" endpoint yet. That's the last piece of the audit workflow.
- **`react-native-keyboard-aware-scroll-view` → `react-native-keyboard-controller` migration.** Tracked in [#27](https://github.com/RepublikeIO/republike-mobile/issues/27). The old library is unmaintained and broken under edge-to-edge.
- **New Architecture migration.** `react-native-iap` 14.4+ requires Nitro + Fabric. We're currently pinned to 13.0.4 (pre-Nitro) to stay on legacy arch. Eventually we need `newArchEnabled: true` across the board, which means validating every native module against Fabric. Not urgent but it's the direction the ecosystem is moving.
