# ADR 0006 — Session + auth storage

**Status:** Accepted (Phase 2)
**Date:** 2026-05-29

## Context

The native apps need to persist the session token across launches, refresh it before expiry, react to revocation (USER_INACTIVE), and expose the current user to every screen.

The RN app uses Zustand + `AsyncStorage` for non-secret state and Keychain (iOS) / EncryptedSharedPreferences (Android) for the token. The native rewrite must:

- Keep the token in the platform secure store (no plaintext to disk)
- Survive force-quit, OS reboots, and OS upgrades
- Survive app updates
- Be wipeable on sign-out

## Decision

### iOS — Keychain via a thin `SessionStorage` protocol

`Core/Session/SessionStorage.swift`:

```swift
public protocol SessionStorage {
    func read() throws -> Session?
    func write(_ session: Session) throws
    func clear() throws
}

public struct KeychainSessionStorage: SessionStorage {
    public init() {}
    public func read() throws -> Session? { ... }
    public func write(_ session: Session) throws { ... }
    public func clear() throws { ... }
}
```

Keychain entry:

| Attribute | Value |
|---|---|
| `kSecClass` | `kSecClassGenericPassword` |
| `kSecAttrService` | `"app.republike.session"` |
| `kSecAttrAccount` | `"current-session"` |
| `kSecAttrAccessible` | `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` |
| Payload | JSON-encoded `Session` struct |

`AccessibleAfterFirstUnlockThisDeviceOnly` means:

- Accessible after the user unlocks the device once per boot
- Not synced to iCloud Keychain
- Not migrated when restoring a backup to a new device → forces re-login on a new device, which is the desired safety posture

### Android — EncryptedSharedPreferences

`core/session/SessionStorage.kt`:

```kotlin
interface SessionStorage {
    suspend fun read(): Session?
    suspend fun write(session: Session)
    suspend fun clear()
}

class EncryptedSessionStorage(context: Context) : SessionStorage { ... }
```

EncryptedSharedPreferences config:

| Setting | Value |
|---|---|
| File name | `republike-session` |
| Master key alias | `republike-session-master` |
| Key encryption | AES256_SIV |
| Value encryption | AES256_GCM |

The master key is generated by Android Keystore; the SharedPreferences file is encrypted at rest. Cannot be read without unlocking the device.

## Session shape

Same on both platforms:

```
struct Session {
    let token: String         // NextAuth JWT
    let refreshToken: String?
    let expiresAt: Date
    let user: User            // snapshot at sign-in time
}
```

`user` is a snapshot, not the live source of truth — `SessionManager` re-fetches `user.getMyUserProfile` on every cold launch to refresh it.

## SessionManager

Sits on top of `SessionStorage`. Exposes:

| | iOS | Android |
|---|---|---|
| Type | `@Observable final class SessionManager` | `class SessionManager(...)` |
| Current user | `currentUser: User?` | `currentUser: StateFlow<User?>` |
| Is authenticated | `isAuthenticated: Bool` | `isAuthenticated: StateFlow<Boolean>` |
| Sign in | `signIn(_:) async throws` | `suspend signIn(session)` |
| Sign out | `signOut() async` | `suspend signOut()` |
| Refresh | `refresh() async throws` | `suspend refresh()` |

Sign-out:

1. Calls `auth.signOut()` on the API client (server invalidates the session)
2. Wipes Keychain / EncryptedSharedPreferences
3. Posts navigation event to coordinator/dispatcher: `goToLanding()`

Token refresh:

1. Single-flight via `Mutex` / actor isolation — concurrent expired-token requests trigger ONE refresh
2. If refresh fails (refresh token expired), call sign-out path

## Consequences

- The token never sits in plaintext on disk.
- On uninstall + reinstall, the user is signed out (Keychain on iOS is cleared on uninstall in iOS 16+; EncryptedSharedPreferences is in the app sandbox).
- Backup-restore on iOS does NOT carry the session (intentional).
- Multi-device sign-out happens via the server-side session invalidation on the next API call.

## Alternatives considered

- **iOS DataProtection file storage** (`NSFileProtectionCompleteUntilFirstUserAuthentication`). Cheaper to implement than Keychain. Rejected because Keychain has stronger access semantics and survives binary changes more cleanly.
- **Android `DataStore` (Preferences) with manual encryption.** Considered. Rejected — EncryptedSharedPreferences is the platform-blessed path; rolling our own crypto is the wrong move.
- **Sync session across devices via iCloud Keychain.** Rejected — adds attack surface and complicates revocation.
